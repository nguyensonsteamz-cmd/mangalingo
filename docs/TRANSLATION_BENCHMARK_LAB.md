# Translation Benchmark Lab

Code, data and raw results: `benchmarks/mt/` (re-run with `npm install && node run-all.mjs && node bench-chrome.mjs en-vi && node bench-chrome.mjs vi-en && node adequacy.mjs && node score.mjs && node select.mjs && node report.mjs`).
Evidence class of every number below: **MEASURED on the development machine** unless stated. Nothing is estimated or taken from a paper. **No phone was benchmarked.**

## 1. Environment (the only machine used)
Windows 11 · Intel Core i7-11800H (8 cores / 16 threads) · 15.9 GB RAM · Node 24.18.1 · `@huggingface/transformers` 3.7.6 on `onnxruntime-node` (CPU only; the RTX 3060 was not used because phones have no CUDA) · Chrome (headless) for the baseline. All models run with **beam 4, max 512 new tokens, batch 1**; quantisation q8 (int8).
*Limit:* RSS / latency come from onnxruntime-**node** (native CPU kernels). The shipped build uses onnxruntime-**web** (WASM, single thread), which is slower and uses different memory; the real-browser behaviour was checked functionally in `MT_ENGINE_TEST_REPORT.md` (translation works, the page stays responsive) but latency / RAM of the WASM path were **not benchmarked**.
*Why not Python / sacreBLEU / COMET:* Windows Application Control on this machine blocks unsigned native Python extensions (`numpy` failed to load: "An Application Control policy has blocked this file"). That is a security policy and was not bypassed.

## 4. Metrics
* **chrF++** (char 1–6 + word 1–2, β = 2) and **BLEU** (13a, exponential smoothing) — *re-implemented* from the published definitions in `metrics.mjs`; they follow sacreBLEU's defaults but are **not byte-identical** to sacreBLEU, so compare systems only with each other.
* **Semantic adequacy (proxy)**: cosine similarity of LaBSE (`Xenova/LaBSE@147002d5…`, Apache-2.0) embeddings of the source and the hypothesis. Reported next to the same measure for the human reference ("ceiling"). It is a drift detector, **not** COMET.
* **Terminology consistency**: glossary recall on the long text (lighthouse / keeper / engineer / fishermen / museum / tower / mayor).
* **Degeneration**: share of repeated 4-grams.
* **COMET**: **not run** (needs PyTorch; blocked, see §1). **Fluency / human evaluation**: **not done** (no native-speaker reviewer was available); the categories set is therefore unverified.

## 6. How to read it (and the traps)
* The existing **Chrome Translator** is a strong baseline: ≈ 56 chrF++ in both directions at ≈ 23 ms per sentence. None of the *eligible* open models beats it on quality. That is why the downloaded model is **opt-in / fallback**, not the new default.
* **EnViT5** has the best vi→en quality (59.8) and ties Chrome on en→vi (55.8) but is not eligible (training data licence, see `MT_ENGINE_MODEL_SELECTION.md`). It was also fine-tuned on IWSLT-style data, so its IWSLT score is likely optimistic.
* **M2M-100 418M** is slower than OPUS-MT by ≈ 4–6× per sentence and needs ≈ 2.6 GB RAM: unusable on phones.
* **OPUS-MT en→vi is weak on technical / academic text** (chrF++ ≈ 27 on the unverified category sets) and can drop content ("postponed until Friday" → wrong meaning). vi→en is much better (≈ 54).
* A whole 1,486-character text sent in **one** call comes back at 16–75 % of the reference length for the local models: the 512-token window truncates silently. Chunking is mandatory for them (the app's chunker + the provider's own sentence splitting do this); Chrome Translator handled the whole text (ratio ≈ 1.0).
* Latency of the Chrome baseline excludes its first-use model download (a separate, one-time cost; "cold start" there includes it).
* The M2M-100 vi→en run was first contaminated (other CPU-heavy work ran at the same time: avg 33.9 s) and was **re-run alone**; the table shows the clean run. Every other run happened while the machine was otherwise idle, except for short file edits.
